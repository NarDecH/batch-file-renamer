# RESEARCH — การตัดสินใจเชิงเทคนิคและผลการทดลอง

เอกสารนี้สรุปเหตุผลเบื้องหลังการออกแบบ Batch File Renamer พร้อมผลวัดจริง

## 1. ทำไมต้อง Rust core + Tauri 2

| ตัวเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| Python + PySide6 | เขียนไว | GIL ขัดการสแกนขนาน, ตัวติดตั้งใหญ่ 50–150 MB |
| Electron + Node | Ecosystem ใหญ่ | แรม 200–400 MB, ตัวติดตั้ง 80+ MB |
| **Rust + Tauri 2** ✅ | สแกน/rename ขนานแท้ (rayon/jwalk), ตัวติดตั้ง **1.4 MB**, แรมต่ำ | คอมไพล์ช้า, ต้องระวังรายละเอียดระบบไฟล์ |

ผลจริง: installer NSIS = 1.37 MB, MSI = 1.98 MB

## 2. Performance — ตำแหน่งที่ทำให้ช้าจริง ๆ

### บทเรียนจาก benchmark (สำคัญที่สุด)

รอบแรกวัด preview 10,000 ไฟล์ × 5 กฎ ได้ **3.27 วินาที** — ช้ากว่าเป้า 16 เท่า ตรวจสอบพบสาเหตุ: **กฎ Regex compile pattern ใหม่ทุกไฟล์** (10,000 ครั้งต่อรอบ)

**แก้:** เพิ่ม `RegexCache` (compile ครั้งเดียวต่อรอบ, แชร์ทั้ง pipeline)

| รอบ | เวลา | สัดส่วน |
|---|---|---|
| ก่อนแก้ | 3,270 ms | 1× |
| หลังแก้ | **60.6 ms** | **54× เร็วขึ้น** |

บทเรียน: **วัดก่อนเชื่อ** — ปัญหา performance ของโปรแกรม batch มักไม่ใช่ภาษา แต่เป็นงานที่ทำซ้ำโดยไม่จำเป็น

### เทคนิคที่ใช้จริงในโค้ด

| จุดช้า | เทคนิคแก้ |
|---|---|
| สแกนไฟล์หลักแสน | jwalk สแกนขนานข้าม thread + filter ใน `process_read_dir` |
| ตาราง 100,000 แถว | virtual list — render เฉพาะ ~25 แถวที่มองเห็น |
| พรีวิวตอนแก้กฎ | debounce 200 ms + ยกเลิกรอบเก่า (reactive) |
| อ่าน EXIF/แท็กเพลง | lazy — อ่านเฉพาะเมื่อมีกฎที่ต้องใช้ + cache ต่อ path |
| เช็คชื่อซ้ำ | เทียบใน HashMap ในหน่วยความจำ (ไม่ stat ดิสก์ทีละไฟล์) เช็คดิสก์จริงครั้งเดียวตอน execute |
| ส่งข้อมูลขึ้น UI | event เป็นชุด (ทุก 50 รายการ) ไม่ทีละไฟล์ |

## 3. ความปลอดภัยของข้อมูล — การออกแบบให้ "ไฟล์ไม่หาย"

### ปัญหาที่ต้องแก้ให้ครบ (พบจริงตอนเขียน test)

1. **`std::fs::rename` เขียนทับได้** ทั้ง Windows และ Unix → เช็คปลายทางบนดิสก์ก่อนทุกครั้ง + อนุญาตเฉพาะปลายทางที่เป็น "ชื่อเดิมของอีกไฟล์ในชุด" (chain) และ case-only rename
2. **Cycle rename** (A→B, B→A): rename ตรง ๆ ล้มเหลวเพราะชื่อปลายทางยังถูกใช้อยู่ → ใช้ชื่อชั่วคราว `__rntmp__<uuid>` แล้วรอบสองเปลี่ยนเป็นชื่อจริง โดยเก็บ map temp→final ไว้ตั้งแต่รอบแรก (รอบแรกใช้วิธี parse ชื่อ temp กลับ แล้วพังเพราะ lookup ไม่ตรง)
3. **Journal write-ahead**: เขียน JSON ก่อน rename แรก และอัปเดตหลังทุกรายการ — ปิดโปรแกรม/แครชกลางทาง Undo ได้จากไฟล์เดิม
4. **ยกเลิกกลางทาง**: rollback rename ย้อนกลับทั้งหมดที่ทำไปแล้ว ไม่ทิ้งไฟล์ค้างชื่อ temp

### Grapheme safety (ภาษาไทย)

"น้ำตก" ประกอบด้วย น + ้ + ำ + ต + ก แต่ grapheme cluster จริงคือ ["น้ำ", "ต", "ก"] — ถ้าใช้ `char::indices` ตัด 1 ตัวจะได้ "้ำตก" (สระลอย) ใช้ `unicode-segmentation` ตัด 1 cluster ได้ "ตก" ถูกต้อง — มี test ครอบ (criterion 7)

## 4. Windows-specific ที่ต้องรู้

| ปรากฏการณ์ | การจัดการใน validator |
|---|---|
| ชื่อสงวน CON, PRN, AUX, NUL, COM1-9, LPT1-9 (รวม `con.txt`) | ปฏิเสธ + แจ้งผู้ใช้ |
| อักขระต้องห้าม `\ / : * ? " < > \|` | ปฏิเสธ |
| ชื่อท้ายจุด/ช่องว่าง (Windows ตัดทิ้งเอง) | ปฏิเสธ |
| FS ไม่แยกตัวพิมพ์ | เทียบชื่อซ้ำแบบ case-insensitive แต่ `photo.JPG→photo.jpg` อนุญาต |
| NTFS 255 UTF-16 units | จำกัดความยาวชื่อ |

## 5. Serialization: กฎต้องรอบทาง GUI ↔ engine ↔ ไฟล์ preset

`RuleParams` เป็น enum tagged ด้วย serde (`"type": "regex"`) — ผลวิจัยจากการเจอบั๊ก: frontend เคยส่ง camelCase แต่ serde คาดหวัง snake_case ทำให้ `update_rules` พังตอน runtime (compile ผ่านเพราะ JSON) บทเรียน: **ยึด snake_case ตาม Rust ทั้งระบบ** และเขียนไว้ใน AGENT.md

## 6. สิ่งที่ยังไม่ได้ทำ / ช่องทางต่อยอด

- [ ] Long path (>260 ตัวอักษร) ยังเป็น warning ไม่ได้แก้ registry
- [ ] Romanization ไทย→โรมัน (ฟีเจอร์เสริมตาม spec)
- [ ] Context menu คลิกขวาใน Explorer (ต้อง registry/NSIS customization)
- [ ] Preview แบบ incremental — ตอนนี้คำนวณใหม่ทั้งชุดทุกรอบ (60 ms/10k ยังไหว แต่ 1 ล้านไฟล์ควร diff เฉพาะที่แก้)
